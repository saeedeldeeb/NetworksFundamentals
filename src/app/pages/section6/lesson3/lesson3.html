Lesson 03

TLS (Transport Layer Security)

Without TLS, everything you send — passwords, credit cards, messages — travels as plaintext. Any router between you and the server can read it. TLS solves this with encryption, authentication, and the mathematical guarantee of forward secrecy.

The Problem TLS Solves

HTTP (no TLS)
CLIENT ──── GET /login (plaintext) ────> ROUTER ──── password visible ────> SERVER
HTTPS (TLS)
CLIENT ──── [encrypted ciphertext] ────> ROUTER ──── [encrypted ciphertext] ────> SERVER

Where TLS Sits in the Stack

Layer Protocol
L7 · Application HTTP, WebSocket, …
L5/6 · Session TLS ← here
L4 · Transport TCP
L3 · Network IP

TLS is stateful — it maintains a session with its own variables (keys, sequence numbers, cipher state). This is why it's considered Layer 5 (Session layer) even though it runs on TCP.

Two Types of Encryption

Symmetric
Keys Same key encrypts and decrypts
Speed Fast (XOR-based operations)
Examples AES, ChaCha20
Used for Bulk data encryption
Asymmetric
Keys Public key encrypts, private key decrypts
Speed Slow (exponential math)
Examples RSA, ECDSA
Used for Key exchange and signatures
TLS uses both. Asymmetric encryption is used once — to securely exchange a symmetric key. Then all actual data is encrypted with that fast symmetric key. You get the security of asymmetric with the speed of symmetric.

The Forward Secrecy Problem

Older TLS 1.2 implementations used RSA key exchange: the client encrypts a random symmetric key with the server's public key. This works — but has a fatal flaw.

1
Attacker records everything

An ISP or state actor records years of encrypted TLS traffic. They can't read it yet — but they save it.

2
Private key leaks (Heartbleed, 2014)

A bug in OpenSSL crashed the TLS library and dumped server memory — including private keys. With RSA, one leaked key decrypts all past sessions.

3
Diffie-Hellman solves it

Each session uses a fresh ephemeral key pair. Even if one session's key leaks, all other sessions remain secure — this is Perfect Forward Secrecy (PFS).

Diffie-Hellman Key Exchange

Both parties compute the same shared secret without ever sending it over the wire. The attacker sees the public values but cannot recover the secret due to the Discrete Logarithm Problem (computationally infeasible for large primes).

Watch concrete values travel between the two sides — using small real numbers you can verify by hand. The attacker intercepts every value but still cannot derive the secret key.

TLS 1.2 vs TLS 1.3 Handshake

TLS 1.3: 0-RTT

For repeat connections, TLS 1.3 supports a Pre-Shared Key (PSK) from the previous session. The client can send encrypted data in the very first message — zero additional round trips.

0-RTT trade-off: Replay attacks become possible. An attacker can re-send the first encrypted message and trigger the same server action. Only safe for idempotent requests (GET, not POST). Use with care.

Total RTT Cost

TCP Handshake +1 RTT always required
TLS 1.2 handshake +2 RTT = 3 RTT before first byte
TLS 1.3 handshake +1 RTT = 2 RTT before first byte
TLS 1.3 with 0-RTT +0 RTT = 1 RTT — TCP only, replay risk
Key insight: TLS latency is why HTTP/3 and QUIC were invented. QUIC combines the transport handshake and the encryption handshake into a single step, eliminating the extra round trips entirely. Understanding TLS latency makes QUIC's design obvious: don't do TCP + TLS sequentially — do them simultaneously.
