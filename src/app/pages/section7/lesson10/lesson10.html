Lesson 10

Layer 4 vs Layer 7 Load Balancing

Every load balancer is a reverse proxy, but not every load balancer reads what it's forwarding. The choice between Layer 4 and Layer 7 is a single question with a huge downstream impact: do you want to understand the bytes flowing through?

Where in the Stack?

The OSI layer names are the giveaway. A Layer 4 balancer works at the transport layer — it only sees IPs, ports, and TCP segments. A Layer 7 balancer works at the application layer — it parses HTTP requests, reads headers, looks at paths and cookies, and routes on what it finds.

Same physical role (sit between client and backend), totally different mental model. L4 is a smart wire. L7 is a polite waiter who reads the order, decides which kitchen handles it, and walks it over.

Per-Connection vs Per-Request Routing

The biggest behavioural difference: L4 picks a backend once per connection — every segment after that follows the same path. L7 picks a backend once per request — the same client connection can fan out to many different services:

Aspect Layer 4 Layer 7
Sees IP, port, segments Full HTTP request
Routing unit Connection Request
Sticky? Per connection No — per request
TLS Passes through Must terminate
Protocol aware? No Yes
Caching No Yes

How L4 Actually Forwards

L4 doesn't reassemble anything — it just rewrites the IP/port headers and forwards the raw segment. It keeps a mapping table so return traffic finds its way home:

Direction Header rewrite
Client → LB src: 1.2.3.4 · dst: LB (44.1.2)
LB → Backend src: 44.1.2 · dst: backend (44.1.3) · bytes unchanged
Backend → LB Reverse path — LB consults mapping table
LB → Client src: 44.1.2 · dst: 1.2.3.4 · bytes unchanged

How L7 Actually Forwards

L7 has to understand what's coming in, which means it has to buffer enough bytes to see a complete request before it can decide anything:

  1. Receive segments — collect TCP segments from the client
  2. Buffer until complete — wait for an HTTP request boundary (the blank line after headers)
  3. Parse and inspect — method, path, host, auth header, cookies
  4. Route — /posts/* → Posts service, /users/* → Users service
  5. Forward — send the request over a (possibly pooled) backend connection
L7 buffering is the source of both its power and its cost. It can route, cache, and authenticate at the edge precisely because it reads everything — but reading everything means CPU, memory, and a brief stall before the bytes can flow.

Backend Connection Efficiency

This is the under-appreciated win for L7. Because L4 ties one client connection to one backend connection, every active client occupies a backend slot. L7 can multiplex many client requests over a shared pool of backend connections — far better utilisation when the backend's per-connection cost is high (databases, slow handshakes):

Model Effect
L4 — 1:1 N clients = N backend connections (depletion risk)
L7 — N:M pool Many clients share a small backend pool

TLS Termination — The Other Big Divider

L4 can't read the bytes if it wanted to — they're encrypted, and the LB doesn't have the key. L7 must have the key, because it has to read the request to route it. That places the TLS certificate in two very different homes:

Property L4 (pass-through) L7 (terminate)
Where cert lives On every backend Only on LB
What LB sees Encrypted bytes Plaintext request
Backend CPU for TLS Per-backend cost Zero (plain HTTP internally)
Cert rotation Every backend One place
Privacy from LB op LB can't read traffic LB sees everything

WebSocket: The Sneaky Downgrade

An L7 LB happily routes Upgrade: websocket — but the moment the upgrade completes, the connection becomes a long-lived bidirectional byte stream that the LB can't parse anymore. From that point on it's de facto L4: any auth, rate-limit, or path rule the LB enforced for HTTP requests no longer applies.

Watch out: if your security model depends on L7 rules at the edge, an attacker who can convince the LB to upgrade can run anything they like over the resulting tunnel. Enforce auth on the upgrade request before it succeeds, or apply backend checks after.

When to Use Which

Use case L4 L7
Plain TCP services (databases, custom protocols) ✓ —
End-to-end encryption required ✓ —
Maximum throughput / minimum latency ✓ —
HTTP APIs, path-based routing — ✓
API gateway, auth at the edge — ✓
Caching, response rewriting — ✓
Few backend connections, many clients — ✓

Summary

Aspect Layer 4 Layer 7
Understands TCP segments HTTP requests
Routes by Connection (5-tuple) Request (path, headers, cookies)
TLS handling Pass-through Termination required
Backend conns 1:1 with clients Pooled, multiplexed
Overhead Minimal — just forward Parse, decrypt, route
Best fit Any protocol, raw speed HTTP, smart routing
Key insight: Layer 4 treats data as opaque — fast, secure, dumb. Layer 7 understands the protocol — powerful, smart, but must hold the keys and pay the CPU. The L4 vs L7 choice is really about how much intelligence you want at the edge: a smart wire, or an opinionated gateway.
