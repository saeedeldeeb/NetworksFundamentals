Lesson 11

Network Access Control for Databases

Almost every database leak that makes the news has the same root cause: somebody left the database reachable from anywhere on the internet, with no network-level filter in front of it. The password becomes the only thing between attackers and your data — and the password is never the strongest link.

The Problem in One Sentence

Database engines have great authentication. What they don't have, out of the box, is a guarantee about who can even speak to the port. That's a network problem, not an auth problem — and it needs network-layer answers.

Headlines you've seen: “Elasticsearch cluster leaks tens of millions of users.” “700 MongoDB instances exposed, terabytes downloaded.” Almost always: bindIp = 0.0.0.0, no IP allowlist, no firewall in front.

Defense in Depth — Two Walls, Not One

A well-configured database has two independent network-level controls. Either one alone can save you; together they're how production databases are supposed to be deployed.

Layer Question it answers Where it lives
1 — listen addresses Which NICs does the DB bind to? postgresql.conf, mongod.conf, my.cnf, redis.conf
2 — host-based auth Which client IPs are allowed? pg_hba.conf, user@host grants, bindIpAll
Wall 1 is about reachability: a packet from a wrong-NIC source never even arrives. Wall 2 is about authorisation: even if the packet arrives, the DB checks whose IP it's from before reading the username. Misconfigure one — the other still blocks the attack.

PostgreSQL: pg_hba.conf

Postgres reads this file top-to-bottom and uses the first matching rule. Each row is a small policy: who's connecting, how (TCP or unix socket), from where, and how they should authenticate:

Column What it controls
TYPE local = unix socket · host = TCP · hostssl = TCP w/ TLS only
DATABASE / USER Limit a rule to specific DBs or roles (or all)
ADDRESS CIDR like 10.0.0.0/24 — the network-level allowlist
METHOD scram-sha-256, md5, cert, peer, trust, reject

Local Unix Socket vs Loopback

Two different things people often conflate — both stay on the same machine, but they go through different parts of the kernel:

Connection Path Cost
local — unix socket Direct IPC, no TCP stack at all Fastest possible
host 127.0.0.1 — loopback Full TCP stack, just routed to lo Same-machine but with TCP overhead

CIDR Notation — Reading the Allowlist

The /N suffix is the heart of the allowlist. It says "the first N bits must match this address; the rest can be anything." Same rule, three very different attack surfaces:

CIDR Matches How big
127.0.0.1/32 Exactly one host 1 IP
10.0.0.0/24 A /24 subnet 256 IPs
10.0.0.0/16 A /16 — large internal network 65,536 IPs
0.0.0.0/0 Every IPv4 address that exists ~4.3 billion
IPv4 vs IPv6 loopback are different addresses. 127.0.0.1/32 only covers IPv4; if anything on the host connects via ::1 you also need ::1/128. The string localhost can resolve to either, so be explicit in the config rather than trusting DNS.

Listen Addresses — Wall 1 in Practice

Where the database binds matters as much as who you allow. A DB that's not bound to a public NIC is invisible from the public internet even if a firewall rule slips:

Common Mistakes

Mistake Consequence
listen_addresses = '*' in prod DB reachable from every NIC, including public ones
host all all 0.0.0.0/0 Allowlist becomes "the entire internet"
"Just testing" with trust No password at all — and configs always ship
Copying dev config to prod Loose dev rules leak into production
Weak password + open allowlist Bots find you in hours, not days

The Attack Timeline

Whatever the database is, every breach follows the same three steps. Your job is to make sure the attacker fails at step 1 or step 2 — because if they make it to step 3, the only thing left is a password, and bots try common pairs (postgres/postgres, admin/admin) at industrial speed:

Step What stops it
1. Scan internet for open port 5432 listen_addresses (Wall 1) — port not even bound
2. Open TCP connection, send startup packet pg_hba.conf (Wall 2) — IP not on allowlist
3. Guess passwords until one works Only password strength — this is where breaches happen

Best Practices

Practice Why
Bind to the smallest set of NICs Cuts off most of the attack surface for free
Allowlist by /32 for known hosts No subnet drift, no surprises
Use /24 for cohort of app servers Lets autoscaling work without per-instance edits
Default deny — let the implicit reject catch the rest Anything not explicitly allowed is blocked
Separate dev / staging / prod configs Loose dev rules never reach prod by copy-paste
Audit the allowlist regularly Old hosts and decommissioned subnets pile up

It's the Same Idea Everywhere

Different engines, same two walls — different setting names:

Engine Wall 1 (listen) Wall 2 (allow)
PostgreSQL listen_addresses pg_hba.conf
MySQL bind-address User grants with 'user'@'host'
MongoDB net.bindIp / bindIpAll Role-based + IP whitelist (Atlas)
Redis bind protected-mode, ACLs
Elasticsearch network.host X-Pack security / API keys

Summary

Control What it does
listen addresses Decides which NICs the DB binds to
pg_hba ADDRESS (CIDR) Decides which source IPs may attempt to authenticate
/32 suffix Exact-host rule — recommended for known servers
/24 suffix Subnet rule — sensible for a cohort
reject method Explicit block above a broader allow rule
Implicit final rule Anything not matched is denied
Key insight: Database breaches don't usually happen because someone broke the crypto. They happen because a "just testing" configuration shipped to production and the database accepted connections from the entire internet. Configure both walls — what you listen on, and who can connect — and the password never has to do the hard work alone.
