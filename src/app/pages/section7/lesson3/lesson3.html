Lesson 03

Nagle's Algorithm

Your network is fine. Your server responds instantly. But something is adding a mysterious 50–200ms delay to certain operations and you can't find it in your code or your logs. The culprit is inside the TCP stack itself — and it's been there since 1984.

Why It Was Invented — The Telnet Problem

In 1984, John Nagle noticed that interactive Telnet sessions were flooding the network with tiny packets. A user typing ls would generate three separate TCP segments — one for l, one for s, one for \n. Each one: 1 byte of data, 40 bytes of IP+TCP headers.

Packet Breakdown
1 byte of data 40B of IP+TCP headers — 97.6% overhead
3 characters typed 3 packets × 41B = 123B sent for 3B of data (2.4% efficiency)
With Nagle: buffered 1 packet: 40B headers + 3B data = 43B (7% overhead instead of 97.6%)

Nagle's solution: don't send small segments if there's already unacknowledged data in flight. Buffer them until either the segment fills to MSS, or an ACK arrives for the outstanding data. Problem solved — for 1984 Telnet.

Nagle's Three Rules

1
No unacknowledged data in flight → send immediately

First write always goes out right away. Nothing in flight means no risk of flooding.

2
Segment is full (≥ MSS bytes) → send immediately

Full segments ship regardless. No buffering needed — the efficiency goal is already met.

3
Otherwise → buffer and wait

If the segment is partial AND there's unacked data, Nagle holds the bytes until the segment fills to MSS or an ACK arrives unlocking the buffer.

The Catch — When Nagle Hurts You

Rule 3 is the problem. When you send 5000 bytes, three full segments (3 × 1460B) fire immediately — but the last 620 bytes get stuck. There's unacked data in flight, and 620 < 1460, so Nagle buffers it. The only way out is to wait for an ACK. That wait is exactly one round-trip time — non-deterministic, invisible, and hard to debug.

The Solution: TCP_NODELAY

TCP_NODELAY = 1 tells the OS kernel: "bypass Nagle's algorithm entirely. Send every write immediately, no buffering, no waiting." It trades a tiny amount of bandwidth efficiency for predictable, low-latency behavior. For almost every modern application, this trade is worth it.
Setting Behavior
TCP_NODELAY = 0
(default) Nagle on — buffers partial segments. Good for bulk throughput, bad for latency.
TCP_NODELAY = 1 Nagle off — every write exits the kernel immediately. Predictable latency.

When to Disable Nagle's Algorithm

Scenario Recommendation
Real-time apps (games, chat, video) Disable — latency is the metric, not throughput
Interactive protocols (SSH, terminals) Disable — every keystroke must feel immediate
HTTP APIs (REST, GraphQL) Disable — request headers + body rarely align perfectly to 1460B
TLS handshakes Disable — handshake messages are small; Nagle causes stalls
Bulk file transfers Optional — full segments fire regardless; Nagle only affects the tail
High-latency links Disable — higher RTT = longer wait for partial segments
Where to set it: The sender sets TCP_NODELAY. For an HTTP server, that's the server side. For a database client, that's the client library (most modern drivers like pg, mysql2, and redis clients enable it by default). For a custom protocol: both sides may benefit.
Key insight: Nagle's algorithm solved a real 1984 problem — today, bandwidth is cheap and latency is the bottleneck. Most modern applications benefit from TCP_NODELAY. The 40-byte header "waste" per small segment is irrelevant compared to adding 50–200ms of unpredictable delay to every partial write.
