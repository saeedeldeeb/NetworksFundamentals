Lesson 04

Delayed Acknowledgment

Nagle's algorithm delays sending from the sender. Delayed ACK delays sending from the receiver. Each one alone causes minor inefficiency. Together, they create a deadlock that can freeze data transfer for 400ms — invisible in your code, silent in your logs, and maddening to debug.

What Is Delayed ACK?

By default, a TCP receiver doesn't acknowledge every segment immediately. Instead, it waits briefly — hoping either another segment arrives (so one ACK covers both) or that it has data to send back (so the ACK can piggyback on an outgoing segment). This reduces ACK traffic at the cost of acknowledgment latency.

Mode Behavior
Without Delayed ACK 5 segments → 5 ACKs. Each ACK is its own packet. Accurate but generates traffic.
With Delayed ACK
(default) 5 segments → 1 ACK. Wait up to 200ms, then batch-acknowledge everything received so far.
The RFC recommendation: wait at most 500ms before sending an ACK, and send an ACK for every second full-size segment. Linux and most OSes use 40ms as the minimum timer and 200ms as the maximum — but these values vary by OS and kernel version.

Why It Was Designed

1
Reduce ACK traffic

An empty ACK packet is 40 bytes of IP+TCP headers for zero bytes of useful data. Batching ACKs reduces the ratio of overhead packets on the network.

2
Piggyback ACKs on outgoing data

In bidirectional protocols (like HTTP/1.1 request-response), the receiver often has data to send back anyway. The ACK rides in the header of that response for free.

3
Reduce CPU interrupts

Every packet triggers a kernel interrupt. Fewer ACK packets means fewer interrupts, which matters at the thousands-of-connections scale.

The Deadly Combination — Nagle + Delayed ACK

Both algorithms were designed in the same era for the same goal: reduce unnecessary packets. The designers didn't anticipate what happens when both run simultaneously on opposite ends of the same connection. The result is a true deadlock:

The 400ms Breakdown

Component Time Added
Delayed ACK timer ~200ms (RFC recommendation, varies by OS)
Nagle's waiting period Variable — waits indefinitely until ACK or MSS
Network RTT 1ms (same DC) to 300ms+ (cross-continent)
Total potential delay 200ms to 400ms+ per partial segment
This is non-deterministic. The delay depends on the Delayed ACK timer value (varies by kernel), the RTT, and whether any other segments arrive to trigger an early ACK. You might see 40ms in development and 350ms in production — the same code, different OS tuning.

Nagle vs Delayed ACK — Side by Side

Aspect Nagle's Algorithm Delayed ACK
Acts on Sender side Receiver side
Delays Sending small segments Sending ACKs
Socket option TCP_NODELAY TCP_QUICKACK (Linux)
Goal Fill segments before sending Batch ACKs to reduce traffic
Together Deadlock — both waiting on each other — up to 400ms delay

The Solution

Problem Fix
Nagle delays sending partial segment Set TCP_NODELAY = 1 on sender
Delayed ACK holds back acknowledgment Set TCP_QUICKACK = 1 on receiver (Linux)
Both enabled → deadlock Disable at least one. Prefer both disabled for latency-sensitive apps.

Diagnosing the 200ms Trap

Real-world pattern: You see a request that takes 250ms even though your server processes it in 2ms. You check CPU, memory, database — all fine. The culprit is the Nagle + Delayed ACK deadlock on the final segment of the response. The fix: setNoDelay(true) on the server socket. Zero other code changes. 250ms drops to 3ms.
Key insight: Nagle and Delayed ACK are both individually reasonable optimizations for high-latency, bandwidth-constrained 1980s networks. In 2024, bandwidth is cheap and the internet is fast. The 40-byte ACK savings cost you 200ms of latency — a terrible trade. Most high-performance servers, HTTP clients, and database drivers now disable both by default. If you're building a latency-sensitive system and haven't explicitly set TCP_NODELAY, you're probably leaving performance on the table.
