Lesson 06

TCP Fast Open

The previous lesson showed how connection pooling avoids paying the handshake cost repeatedly. TCP Fast Open takes a different angle: instead of avoiding the handshake, it makes the handshake itself useful — letting your request data ride along with the very first packet.

The Problem: Empty Handshakes

A normal TCP handshake exchanges three packets before a single byte of application data moves. And those three packets are empty — they carry only flags and sequence numbers. They exist purely to agree that a connection is open.

Packet Payload
SYN → Empty — flags + sequence number only
← SYN-ACK Empty — flags + sequence number only
ACK → Empty — acknowledgment only
Actual data → The 4th packet — sent only after all three empties

The Idea: Send Data During the Handshake

"I already know this server. I've connected to it before. Why can't I just send my request data along with the SYN?"
That question is exactly what TCP Fast Open (TFO) answers — defined in RFC 7413 and shipping in the Linux kernel since 3.13.

How It Works: The Cookie

TFO can't let anyone send data with a SYN — that would be a gift to attackers spoofing source IPs. So it uses a cookie: an encrypted token the server issues on the first connection and the client presents on every connection after. The cookie proves "this client has talked to me before."

Cookie Property Description
Storage TCP header options field — makes the header > 20 bytes
Generated by The server
Encrypted Yes — encrypted by the server, opaque to the client
Purpose Proves the client genuinely connected before
Prevents SYN-flood attacks from spoofed source IPs

Normal vs Fast Open

Once the client holds a valid cookie, every later connection collapses the "handshake then data" sequence into a single combined exchange. Watch the request data leave on the SYN — and the response come back on the SYN-ACK:

Aspect Normal TCP TCP Fast Open
First data sent After the 3rd packet (ACK) With the 1st packet (SYN)
RTT before data 1.5 RTT 0 RTT
Requires Nothing Prior connection + cookie
Cookie storage N/A TCP options field

Best Use Case: The TLS Handshake

TFO saves one RTT — which sounds modest until you remember what usually comes right after the TCP handshake: the TLS handshake. With TFO, the client can put its TLS ClientHello in the SYN, so encryption negotiation starts a full round-trip earlier.

Normal: SYN → SYN-ACK → ACK → ClientHello → ServerHello → …

With TFO: SYN + ClientHello → SYN-ACK + ServerHello → …

The TCP and TLS handshakes overlap instead of running back-to-back — a full RTT shaved off every new HTTPS connection.

Browser Connections — Six in Parallel

HTTP/1.1 browsers open up to six parallel TCP connections per host to fetch resources concurrently. Without TFO, that's six full handshakes before the page can start loading.

Without TFO With TFO
6 × full handshake before any data 1 normal handshake earns the cookie
6 × 1.5 RTT of pure setup latency 5 connections send their request with the SYN
Slowest experience on the first visit Near-instant connection setup on every repeat visit

Enabling TCP Fast Open

Fast Open ≠ Skipping Slow Start

The name causes a common misconception. "Fast Open" sounds like the connection skips straight to full speed — but it does not.

Two different problems, two different mechanisms:

TCP Fast Open sends data during the handshake — it attacks connection latency.
Slow start ramps the congestion window gradually — it attacks network congestion.

You still get slow start with TFO. The connection opens a round-trip sooner, but throughput still climbs gradually over the first several RTTs. TFO never promised otherwise.

Summary

Feature Benefit
Data in the SYN No waiting for the handshake to complete
Cookie-based Secure — proves a genuine prior connection
1 RTT saved Significant on high-latency, long-distance networks
TLS optimization The ClientHello can ride along immediately
Linux default Enabled since kernel 3.13
Key insight: TCP Fast Open saves a full round-trip by sending data with the SYN packet — but only for repeat connections. The first connection still needs a normal handshake to exchange the cookie. TFO is an optimization for the path you travel often, not the path you travel once. Combined with connection pooling from the previous lesson, it's how high-performance systems drive connection setup cost toward zero.
