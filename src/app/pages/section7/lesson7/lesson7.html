Lesson 07

Listening Servers

Every server you write begins with a single line: listen(port, address). That innocent-looking address argument decides whether your service is reachable from the same process, from your laptop, from the LAN, or from the entire public internet. Get it wrong on a misconfigured box and you'll find your unauthenticated admin panel on a breach-data site within hours.

What "Listening" Really Means

A listening socket is identified by two things — not just the port:

You pick What it controls
An IP address Which network interface the kernel will accept packets on
A port Which specific service on that interface

Your machine almost always has multiple IP addresses at once — and the address you bind to is the one (and only one) that incoming connections can reach:

Interface Typical IP Reachable from
Loopback (IPv4) 127.0.0.1 Same machine only
Loopback (IPv6) ::1 Same machine only
LAN / WiFi adapter 192.168.x.x Same local network
Docker bridge 172.17.x.x Container network
All interfaces 0.0.0.0 / :: Everything reachable — including public

Real-world incident pattern: Elasticsearch, MongoDB, and Redis defaults used to bind to 0.0.0.0 with no authentication. Operators ran them on cloud VMs with public IPs, no firewall rules, and assumed "it's only the dev port." Internet-wide scanners found tens of thousands of unauthenticated databases — that's how the recurring "10 million records leaked" headlines happen.

Listening Scenarios — Who Can Reach You

Listen address Who can connect
127.0.0.1:8080 Only the same machine (IPv4)
[::1]:8080 Only the same machine (IPv6)
192.168.1.10:8080 Only via that specific interface
0.0.0.0:8080 Anyone who can reach ANY interface
[::]:8080 IPv6 equivalent of 0.0.0.0 — everywhere

IPv4 vs IPv6 Loopback Are Different Addresses

A server bound to 127.0.0.1 will refuse a connection to [::1], even though both are "loopback." They live on separate sockets:

Server bound to Client connects to Result
127.0.0.1:8080 http://127.0.0.1:8080 ✓ Works
127.0.0.1:8080 http://[::1]:8080 × Connection refused
::1:8080 http://[::1]:8080 ✓ Works
::1:8080 http://127.0.0.1:8080 × Connection refused
"It works in curl but not in my browser": that's almost always this. localhost is a DNS label — your OS may resolve it to either 127.0.0.1 or ::1 depending on /etc/hosts and resolver order. If your server only listens on one of the two, the other resolution silently fails. Always bind explicitly — 127.0.0.1 or ::1 — instead of trusting the label.

IPv6 URL Syntax

IPv6 addresses contain colons, which collide with the host:port separator. URLs solve this with square brackets:

Family URL form
IPv4 http://192.168.1.10:8080
IPv6 http://[::1]:8080 — brackets required

The Socket Identity: (IP, Port) Pair

A listening socket is uniquely identified by the pair, not the port alone. That means the same port can be used by multiple processes — as long as each one binds to a different IP. But two processes can't share the exact same pair, and the kernel will say so loudly:

The Exception: SO_REUSEPORT

High-throughput servers like nginx and HAProxy need many worker processes listening on the same port. The kernel offers an opt-in socket option, SO_REUSEPORT, that lets multiple processes share one (IP, Port) pair. The kernel then hashes the connection's 4-tuple (source IP, source port, dest IP, dest port) to pick which worker handles each new connection — load balancing for free, in kernel space.

Watch the failure mode: if a worker dies, the hash table shrinks and active connection ownership may shift to a different worker. The connections that were in progress on the dead worker are gone — and any state that wasn't shared (sticky sessions, in-memory caches) goes with them. SO_REUSEPORT is a load balancer, not a cluster manager.

Best Practices — Where to Bind

Scenario Listen on
Solo development 127.0.0.1 — keeps the cafe Wi-Fi out of your dev server
Team development on LAN Specific LAN IP, or 0.0.0.0 with caution
Admin / debug interfaces 127.0.0.1 ONLY — never public, regardless of "auth"
Public services Specific interface, or 0.0.0.0 behind a firewall
Container processes 0.0.0.0 inside the container — isolation lives at the container boundary

Summary

Concept Description
(IP, Port) pair The real identity of a listening socket
0.0.0.0 All interfaces — dangerous default for anything sensitive
127.0.0.1 IPv4 loopback — same machine only
::1 IPv6 loopback — same machine only
localhost DNS label — may resolve to IPv4 OR IPv6 depending on OS
SO_REUSEPORT Lets multiple processes share one port; kernel hashes the 4-tuple
Key insight: "listen on everything" is the kind of default that's convenient in development and catastrophic in production. The right question is never "which port?" — it's "which interface?". Pick the narrowest one that lets the callers you actually want reach you. Every data-leak headline about an exposed database starts with someone binding to 0.0.0.0 and assuming nobody would notice.
