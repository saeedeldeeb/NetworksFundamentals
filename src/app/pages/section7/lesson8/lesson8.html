Lesson 08

TCP Head-of-Line Blocking

TCP's biggest selling point — strict in-order delivery — is also its sharpest edge. The moment you start sending independent things through the same connection, a single dropped packet brings everything else to a halt. The feature is the bug.

TCP's Ordering Guarantee

TCP delivers bytes to the application in order. Segments that arrive out-of-sequence aren't given to the application — they're parked in a reorder buffer. Nothing past the missing byte is allowed through until the gap is filled.

That guarantee is exactly why TCP is easy to program against. You read from a socket and you get a clean, ordered byte stream. The cost is hidden: anything sitting behind a lost segment in that stream gets held back too — even if it would otherwise be ready.

The Problem Gets Worse with Multiplexing

HTTP/2 had a great idea: instead of opening six parallel TCP connections like HTTP/1.1 did, multiplex many independent requests over one TCP connection. Less handshake overhead, less memory, less head-of-line blocking at the HTTP layer.

Layer What it sees
Application (HTTP/2) Independent streams — request 1, request 2, request 3, …
Transport (TCP) One continuous byte stream — no concept of "stream"

HTTP/2 knows requests 2 and 3 have nothing to do with request 1. TCP doesn't. So when a segment belonging to request 1 is lost, TCP refuses to deliver any bytes past it — including the bytes that finish requests 2 and 3 entirely.

The amplification: open one HTTP/2 connection that's multiplexing ten requests. One stray dropped packet blocks all ten — even if nine of them are complete and waiting in the receiver's buffer. Multiplexing turned a per-request problem into a per-connection problem.

Impact at Different Scales

Scenario Effect
1 lost segment All bytes behind it on the connection are stalled
High packet loss Pathological latency — every loss restarts the stall
Many multiplexed streams More victims share the same fate
Long-distance / high-RTT links Each retransmit costs another full RTT before unblock

Wait time is roughly 1 RTT to detect the loss + 1 RTT for the retransmit to arrive. On a 200 ms transcontinental link, that's nearly half a second of stalled application traffic from a single dropped packet.

HTTP/1.1 vs HTTP/2 vs HTTP/3

Protocol Connection model Head-of-line behaviour
HTTP/1.1 6 parallel TCP connections Each connection's loss only hurts its own requests
HTTP/2 1 TCP connection, multiplexed A loss anywhere blocks every stream on the connection
HTTP/3 QUIC over UDP, per-stream ordering Only the affected stream blocks — others keep flowing
Notice the irony: HTTP/1.1's six-parallel-connection model — the very thing TFO and connection pooling are designed to soften — was also accidentally protecting it from this problem. HTTP/2 fixed the connection cost and revealed the transport-layer issue underneath.

The Fix: Move Stream Awareness Down the Stack

QUIC (the transport beneath HTTP/3) inherits TCP's reliability and congestion control but re-implements them per stream. A QUIC connection isn't one ordered byte stream — it's many ordered byte streams sharing a connection. A loss on stream 1 only blocks stream 1; streams 2 and 3 are delivered the moment their packets arrive.

Property TCP QUIC
Lives in Kernel User space (over UDP)
Stream concept None — one byte stream First-class — many independent streams
Loss on stream X Blocks the whole connection Blocks only stream X
Encryption Optional (TLS bolted on top) Mandatory — TLS 1.3 baked in
Handshake cost TCP + TLS = up to 3 RTTs Combined — 1 RTT (or 0 with cached params)

What This Means in Practice

Situation What to do
Mostly-clean network, low RTT HTTP/2 over TCP is fine — loss is rare enough that HoL barely shows
Mobile, lossy, high-RTT users HTTP/3 / QUIC — the per-stream model pays off the most here
Many small parallel requests HTTP/3 — multiplexing without the shared-fate penalty
Long-lived bulk transfers TCP is fine — there's only one logical stream anyway

Summary

Aspect TCP behaviour
Ordering Strict, in-order delivery
Lost segment All subsequent bytes are blocked on the connection
Multiplexing Amplifies the cost — many requests share one fate
HTTP/2 impact Independent requests blocked by unrelated loss
HTTP/3 / QUIC solution Stream awareness in the transport — per-stream ordering
Key insight: TCP's ordering guarantee is the right tool for one ordered stream and the wrong tool for many. The moment HTTP/2 multiplexed independent requests over a single TCP connection, it inherited a problem TCP can't see — and the only real fix was to push stream awareness all the way down into the transport, which is exactly what QUIC does.
