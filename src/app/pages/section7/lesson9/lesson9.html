Lesson 09

Proxies & Reverse Proxies

A proxy and a reverse proxy are the same machine pointed in opposite directions. The thing that changes is which identity is hidden: a forward proxy hides the client, a reverse proxy hides the server. Once you see them that way, every term in modern infrastructure — CDN, load balancer, API gateway, service mesh — clicks into place.

The Core Difference, in One Table

Type Client knows the destination? Server knows the client?
Forward proxy Yes — picked it on purpose No — sees the proxy's IP
Reverse proxy No — sees the proxy as the server Yes — receives client info

What a Forward Proxy Is For

A forward proxy is something the client opts into. It's configured in the browser, on the OS, or in a corporate device policy. Once configured, every outbound request goes through it before reaching the real destination.

Use case What it gives you
Anonymity Hide the client's IP from the destination
Caching Corporate proxy serves common responses without re-fetching
Logging Audit every outbound request the org makes
Blocking Drop requests to disallowed hosts at the perimeter
Debugging Fiddler / Charles intercept and rewrite HTTP for inspection
Service mesh Envoy / Linkerd sidecars proxy every microservice call

The Layer 4 vs Layer 7 View

At Layer 4, a proxy is just two TCP connections — one with the client, one with the upstream — that pass bytes between them. At Layer 7, it actually parses the HTTP and decides what to do based on the request:

Forward proxy example:
L4: client ↔ proxy and then proxy ↔ google.com — two independent TCP connections.
L7: client says "take me to google.com" → proxy translates that into its own GET / upstream.

The "two connections, one logical conversation" model is what makes everything else in this lesson possible.

What a Reverse Proxy Is For

A reverse proxy lives on the server side. The client thinks it's talking to the real service; the reverse proxy is the public face of a fleet behind it. Almost every public website on the internet sits behind one.

Use case What it gives you
Load balancing Spread requests across many identical backends
CDN Cache content at edge POPs close to users
API gateway Route /posts to Posts svc, /users to Users svc
TLS termination Decrypt once at the edge; backends speak plain HTTP
Canary / blue-green Send 10% of traffic to a new version, 90% to the old
Authentication Verify tokens at the gate; backends trust the proxy

The Sidecar Pattern (Both at Once)

Modern service meshes (Envoy, Linkerd) attach a proxy to every microservice. It acts as a forward proxy for the app's outbound calls and a reverse proxy for the app's inbound calls — and it handles mTLS, retries, tracing, and metrics transparently. The app code talks to localhost; the sidecar deals with the network.

That's why a service mesh feels like magic: it gives every service free observability and zero-trust networking without changing application code. The cost is one more hop on every request — and a control plane to keep all those sidecars configured.

Proxy vs VPN — Often Confused

Aspect Proxy VPN
Layer L4 / L7 (per protocol) L3 (every IP packet)
Protocol-aware Yes — speaks the protocol No — opaque tunnel
Sees content Yes (unless TLS-tunneled) No — encrypted end to end
DNS Often terminated at the proxy Sent through the tunnel too
Best for "anonymity" Limited — proxy sees plaintext Stronger — full encryption

HTTP CONNECT — The Dumb-Pipe Tunnel

When a forward proxy sees an HTTPS URL, it can't decrypt the traffic (that's the whole point). So it falls back to a tunnel: the client sends CONNECT host:443, the proxy opens a TCP connection to the server, replies 200 Connection Established, and from that point on just shovels bytes back and forth without inspecting them.

Why this matters: CONNECT preserves end-to-end TLS through a proxy. The proxy still sees the destination hostname (it has to, to open the upstream socket), but the body of the conversation stays opaque to it. That's the foundation HTTPS depends on when corporate proxies are in the middle.

Summary

Concept Forward proxy Reverse proxy
Client knows destination? Yes No
Server knows client? No Yes
Configured by The client The server / infra team
Primary benefit Privacy, caching, control of outbound traffic Scaling, routing, security at the edge
Key insight: a load balancer is a reverse proxy, but not every reverse proxy is a load balancer. A CDN is a reverse proxy. An API gateway is a reverse proxy. A service mesh sidecar is both, fused. Once you stop thinking in product names and start thinking in "who's hidden — client or server?", most of the modern stack stops looking like alphabet soup.
